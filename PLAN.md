# YDLidar X3 (non-Pro) — Emulator + 3D Scene + Object Tracker

Status: **plan complete, not yet implemented**. Generated by a multi-agent workflow (3 scouts → 3 designs → 3 judges → 3 skeptics + 33 flaw verifications → synthesis).

## 1. Selected approach

WEBGL — FastAPI + uvicorn[standard] + vendored three.js r185, with an API-level pure-Python emulator (SimLidarSource) that is a duck-typed twin of the installed ydlidar.CYdLidar SWIG module. It won the weighted judge aggregate 7.99 vs pygame 7.70 and serial 6.80, driven by the highest viz quality (9.0), best perf/latency (8.17), and balanced risk (8.0) — the browser avoids Wayland/X11 GL friction on CachyOS, three.js gives the richest scene for free, and the swap-in story (LidarSource ABC + factory + test_swap parity, all keyed to the SDK surface verified from YDLidar-SDK source) is as strong as pygame's while serial's byte-level fidelity is bought at a cost and risk that don't pay off in the weighted total. Every confirmed flaw affecting this approach has a concrete fix incorporated below (y-axis sign fix, r_obj(1+cos β)/2 arc-centroid bias, 0.10 m background threshold, 1-point-cluster gating, 2π/299 inclusive angle grid, footprint clipping, capture-based background calibration, reset control channel).

## 2. Architecture

ONE Python process, TWO threads. (1) Main thread: uvicorn runs the FastAPI app — static mount / → static/, WebSocket endpoint /ws (scene), lifespan startup/shutdown. The game is NOT here — it is a separate desktop process (§10) that imports core/ only. (2) Scan thread (started in lifespan, stopped via threading.Event stop_event): loop = source.doProcessSimple(scan) → Tracker.process(scan) → SceneModel.publish(frame); pacing sleep is stop_event.wait(timeout) so shutdown is prompt; on exit the scan thread itself calls turnOff()/disconnecting() in a finally block (single-writer discipline — the main thread NEVER touches the source; this is the shutdown-race fix). SimLidarSource.doProcessSimple blocks ~100 ms holding the 10 Hz cadence and internally does raycast+noise; RealLidarSource.doProcessSimple blocks up to 1000 ms (fine — dedicated thread). SceneModel is the shared boundary: single-slot latest-wins frame store (threading.Lock, seq counter; stale frames dropped, never queued) PLUS a control channel — a queue.Queue(maxsize=1) that the WS/event-loop thread writes to ({'op':'reset','seed':int}|{'op':'set_object','x','y'}) and the scan thread drains BETWEEN doProcessSimple calls (reset takes effect at the next scan boundary — no tearing; this is the reset-path fix). WS endpoint: per-connection asyncio task; on connect sends hello + scene from SceneModel snapshot; then loops receive with 50 ms timeout, polls SceneModel.latest(seq), sends a frame only when seq changed (stalled/backgrounded client never gets stale replays). Data flow: LidarSource → LaserScan → Tracker (filter → background subtraction via BackgroundTable → cluster → polar centroid + arc-centroid bias → alpha-beta) → Frame (board coords, points clipped to footprint) → SceneModel → WS JSON → browser (three.js, zero trig in browser, latest-wins rAF apply). The game consumes the tracker independently in its own process: Tracker → TapDetector → GameState → renderer (pygame), §10.

## 4. Coordinate frames

CONVENTION: θ=0 = forward, angles increase CLOCKWISE when viewed from top; ray direction d(θ)=(cos θ, sin θ) in the lidar frame (SDK ydlidar_def.h:130-133). FINAL FRAMES: L (lidar): origin at lidar rotation center on the board surface plane (scan plane z=0); +X_L forward (toward the board's back edge), +Y_L starboard (90° CW from forward = off the board's right edge). B (board): origin at the board's FRONT-RIGHT corner = the lidar mount corner, floor level; +X_B along the front edge pointing AWAY from the lidar (toward the front-left corner), +Y_B into the board (toward the back edge), +Z_B up; footprint x_B∈[0,S], y_B∈[0,S] where S = board_size ∈ [1.0, 3.0] m, ALWAYS SQUARE (single scalar — it emulates a square touchscreen/LED panel; CLI --board-size, default 2.0). W (three.js world): right-handed, origin at box floor center; +X_W east, +Y_W up, +Z_W south; board mesh centered at origin spanning x,z∈[−S/2,S/2]. TRANSFORMS (all pure translation/reflection, no rotations): L->B: x_B = y_L, y_B = x_L (lidar forward = +Y_B, starboard = +X_B — the y-axis sign fix: the old webgl design's y_B = W − y_L mirrored the scene and broke real-lidar swap; with the corner origin the transform is the identity swap, no sign flip). POLAR->B: x_B = r·sin θ, y_B = r·cos θ. B->POLAR: r = √(x_B²+y_B²), θ = atan2(x_B, y_B) ∈ [−π, π] (CW-positive). B->W: x_W = x_B − S/2, z_W = y_B − S/2, y_W = 0 (surface). CHECKED EXAMPLES (pinned in test_transforms): θ=0, r=1 → B(0,1) (straight into the board); θ=+π/2 (starboard) → B(1,0) (along the front edge toward front-left); θ=−π/2 (port) → B(−1,0) (off the board's right edge — physically correct, outside footprint); board center B(S/2,S/2) → θ=+π/4, r=S·√2/2 (the sign-fix test: the pygame design's test wrongly asserted −π/4 for a mirrored frame; here atan2(x_B,y_B)=+π/4 is self-consistent with the inverse); B(0,0) lidar → W(−S/2,−S/2); board center → W(0,0). Raycast primitives live in B frame: board edges (x=0, x=S, y=0, y=S over [0,S]) + box walls (x=−1, x=S+1, y=−1, y=S+1; box (S+2)×(S+2) centered on board center) + object circle (r=0.10); raycast in B with d_B(θ)=(sin θ, cos θ). SIZE-RANGE RATIONALE: S ∈ [1.0, 3.0] m — the upper bound is the object-detection budget: the background-subtraction threshold is fixed at 0.10 m = 2.5·σ_r(S·√2) at S=3.0 (σ_r(4.24)=0.040 m) and must stay ≤ the object's 0.10 m radial signature (r_obj = SceneConfig.object_radius, default 0.10 m); σ_r grows as 0.002·d², so for S>3.0 the far-corner noise floor exceeds the threshold and the object becomes invisible to the tracker (§7). Smaller S only lowers σ_max (S=1.0 → far corner 1.41 m, σ=0.008 m; S=2.0 → 2.83 m, σ=0.020 m), so the whole range inherits the S=3.0-verified acceptance; S<1.0 is a toy panel (object/blind-spot dominate). A larger panel would need a larger object — r=0.17 m → S=4.0 m — outside the default range.

## 6. Noise model

NoiseConfig{range_std_a=0.004 (m), range_std_b=0.002 (m/m²), angular_jitter_std=0.0017 (rad ≈ 0.1°), dropout_rate=0.02, ghost_rate=0.001, mixed_pixel_rate=0.15, min_range=0.10, max_range=8.0, enabled=True}. Applied inside SimLidarSource.doProcessSimple in this order: (1) ANGULAR JITTER BEFORE RAYCAST (physically correct): θ' = θ_i + N(0, 0.0017); (2) raycast at θ' → r_true (nearest hit among board edges, box walls, object circle); (3) RANGE NOISE: σ_r(d) = 0.004 + 0.002·d² (m) (Alhashimi ICINCO 2016 heteroscedastic triangulation model), r' = max(0, r_true + N(0, σ_r(d))); (4) DROPOUT: Bernoulli(0.02) → r' = 0; (5) GHOST: Bernoulli(0.001) → r' = |r' + N(0, 0.15)|; (6) BLIND SPOT: r' < 0.10 → 0 (invalid); (7) MIXED PIXELS: with probability 0.15, the arc's two outermost (silhouette) bins blend toward the second-closest hit (wall behind the object) — kept because tracker range-consistency rejection (cluster median + 3σ) removes the bias it would otherwise inject. Resulting σ: 0.012 m at 2 m, 0.020 m at 2.83 m, 0.040 m at 4.24 m (S=3.0 far corner — the worst case over the board-size range; at S=1.0 the far corner is 1.41 m, σ=0.008 m) — within the context's ±2 cm@1–3 m envelope (the quadratic term extrapolates to σ=0.040 m at 4.24 m, which sets the 3.0 m cap). All parameters centralized in NoiseConfig; seeded via np.random.default_rng(seed); tests assert fixed-seed determinism and statistical bounds.

## 7. Tracking

Tracker(config:SceneConfig, noise:NoiseConfig) with set_background(table:BackgroundTable) and process(scan:LaserScan)->TrackResult|None. Per scan: (1) FILTER: keep points with 0.10 < r ≤ 8.0 (r==0 invalid); convert polar->board (x_B=r·sin θ, y_B=r·cos θ). (2) BACKGROUND SUBTRACTION (threshold fix): bg_r(θ) from the calibrated BackgroundTable (sim: startup raycast; real: captured empty-board scans), linear interpolation in θ (real scans have jittered non-uniform angles); object mask = |r_meas − bg_r(θ)| > 0.10 m = 2.5·σ_max at S=3.0 (σ_max = σ_r(4.24 m) = 0.040 m; S=3.0 is the worst case of [1.0, 3.0], so the threshold stays fixed at 0.10 m for every board size — the old 0.03 m was only 0.75·σ_max (~45% per-point FP at the far corner); 0.10 m gives <1% FP per point (verified by Monte Carlo); the threshold also caps S at 3.0 m: it must not exceed the object's 0.10 m radial signature, §4). (3) CLUSTERING: connected components on angle adjacency — angular gap < 3 bins (3·2π/299) AND radial gap < 0.25 m. (4) CLUSTER ACCEPTANCE (min-cluster fix): accept 1-point clusters when they fall within the alpha-beta prediction gate (0.5 m) of the tracked object (at S=3.0 the far-corner arc spans only ~2.2 bins (0.2/(4.24·0.021)=2.24), so single-point scans still occur at the far corner; smaller S widens the arc, S=1.0 → ~6.7 bins; dropping <2-point clusters caused track loss); when untracked, acquire the largest cluster (any size ≥1). Inside each cluster, range-consistency rejection: drop points farther than cluster median + 3·σ_r (kills mixed-pixel pulls and ghosts). (5) CENTROID: inverse-variance weighted polar mean — w_i = 1/(σ_r(r_i)² + 1e−6); θ_m = Σwθ/Σw, r_m = Σwr/Σw. (6) ARC-CENTROID BIAS CORRECTION (the mandated formula): β = asin(r_obj/d̂) with d̂ = r_m; bias = r_obj·(1 + cos β)/2 (≈ r_obj for small β); r̂ = r_m + bias; output position = (r̂·sin θ_m, r̂·cos θ_m). Verified: uncorrected centroid sits ~36–44 mm toward the lidar (the old r²/2d correction left ~35 mm residual — acceptance-failing); with this correction the residual is 5–14 mm and total median error is 11–21 mm across the board. (7) ASSOCIATION: alpha-beta filter (α=0.6, β=0.3, constant-velocity prediction p̂ = p + v·dt, gate 0.5 m); measurement within gate → p = p̂ + α·(z−p̂), v = v + β·(z−p̂)/dt; no measurement or outside gate → missed++, coast p = p̂ with v damped ×0.9 (never teleport); missed > 10 → untracked, re-acquire by largest cluster; dt clamped to [0.05, 0.5] s (absorbs sim/real scanFreq differences). (8) OUTPUT: TrackResult(x_B, y_B, vx, vy, conf=exp(−missed/3), missed, age).

## 8. Swap-in interface

LidarSource(ABC) with abstract methods matching the SWIG surface exactly: setlidaropt(prop, value)->bool, getlidaropt_toInt/toBool/toFloat/toString(prop)->tuple[bool,T], initialize()->bool, turnOn()->bool, doProcessSimple(scan:LaserScan)->bool, turnOff()->bool, disconnecting()->None — PLUS the calibration abstraction (the real-swap fix): calibrate_background()->BackgroundTable, and set_object_pose(xy)->None (sim-only; RealLidarSource implements as no-op). BackgroundTable(angles:np.ndarray, ranges:np.ndarray) with __call__(theta:np.ndarray)->np.ndarray doing linear interpolation — the ONLY way the Tracker reads background (never a raycast, so real mode is defined). Sim: calibrate_background() = noise-off raycast of the empty scene (board + walls, no object). Real: captures N_avg=30 empty-board scans, median per quantized angle bin, then interpolate (real angles are measured per-node with motor jitter — interpolation is mandatory). Factory: make_lidar_source(kind:'sim'|'real', *, scene:Scene, noise:NoiseConfig, seed:int|None=None, port:str|None=None)->LidarSource; selection via CLI flag --lidar; the scan loop, tracker, frames, and WS layer reference only the ABC — zero consumer changes on swap. RealLidarSource delegates to ydlidar.CYdLidar (lazy import; calls ydlidar.os_init()/os_shutdown(); uses the SWIG LaserScan object whose field names are identical to the dataclass, so consumers are agnostic); canonical option block includes LidarPropFixedResolution=True (verified fix: without it the real SDK emits variable-size scans, CYdLidar.cpp:53,625-628). test_swap.py asserts: same method names/signatures on the installed ydlidar module and SimLidarSource; config consistency (max−min)/inc+1 == len(points) == 300; BackgroundTable interpolation round-trip; real-mode tracker path against a recorded scan.

## 10. Game (standalone desktop app, web-free)

A SEPARATE PROCESS from the web viz: `python -m game.run --lidar sim|real [--board-size S] [--image-x FILE] [--image-o FILE] [--resolution PX] [--seed]`. It imports ONLY core/ (lidar + tracker) — no FastAPI, no uvicorn, no WS, no browser; it runs headless-testable without a display (pygame dummy driver in tests) and requires NO web server. PROCESS MODEL: same two-thread shape as the web viz — main thread runs the pygame event loop (draw grid, hover cell, status; handle New Game key), scan thread owns the LidarSource (single-writer shutdown discipline), and the thread boundary is a latest-wins pointer store + a control queue (new_game, quit — drained between doProcessSimple calls, so New Game applies at the next scan boundary, no tearing; the same pattern as the web SceneModel). STATE FLOW: Tracker -> TapDetector.update(track) -> GameState.update on tap -> renderer reads GameState.grid + latest pointer for hover. GAME RULES: 3×3 grid; turn alternates X/O automatically after each tap (single shared pointer — no multi-object tracking); a tap may overwrite ANY cell including the opponent's; win = 3-in-a-row checked after every move (overwrites can break lines, so no per-cell lock); no draw state (a full grid with no 3-in-a-row just continues, overwrites free the cells); New Game clears the grid, resets turn to X, keeps the images. TAP SEMANTICS (touchscreen): a tap is a dwell — the pointer must stay within one cell for 0.3 s (TapDetector), then the move commits and the turn flips; releasing and re-entering a cell re-fires (no auto-repeat while dwelling). CELL ROUNDING: cell = floor(x·3/S), floor(y·3/S) clamped to [0,2] — any point inside a cell's footprint maps to that cell (no dead zones); a pointer outside the board (x,y outside [0,S]²) is not a tap. IMAGES: --image-x/--image-o load PNG/JPG from disk at startup (pygame.image.load → scaled to cell size); when a flag is omitted the renderer draws a vector X/O fallback instead. RESOLUTION: --resolution PX (480/720/1080/1440/2160, default 1080) sets the window/canvas size; grid lines scale with it. GAME EVENTS (for tests): GameEvent dataclass — Tap(x,y,cell,turn), Win(turn,line), NewGame, all emitted by GameState on the scan thread; the renderer consumes them on the UI thread.

## 12. Game renderer (game/render.py)

pygame 2D window — the ONLY UI the game has; no browser, no canvas, no trig. Layout: centered 3×3 grid (cell size = resolution/3); below it a status line (turn, winner, last tap) and a hint (New Game: N). The hover cell is highlighted (pointer in board → that cell, else none). X/O glyphs: the --image-x/--image-o files scaled to the cell (pygame.transform.smoothscale), else vector fallbacks (an X of two lines, an O of a circle). The window is resizable; the grid canvas keeps the --resolution backing size (crisp at any window size). Rendering loop: draw grid → draw glyphs per GameState.grid → draw hover highlight → blit status; runs at the display refresh, decoupled from the 10 Hz scan cadence. No server-side rendering — the game state lives in core/game.py (web-free), the renderer is a pure consumer.

## 15. Confirmed flaws and fixes (incorporated)
All 8 confirmed webgl-design flaws, incorporated: (1) CRITICAL y-axis mirror in lidar->board (y_B = W − y_L mirrored the scene and broke real-X3 swap): fixed by redefining the board frame with origin at the FRONT-RIGHT corner (lidar mount) so L->B is the identity swap x_B=y_L, y_B=x_L; polar->board x_B=r·sin θ, y_B=r·cos θ; pinned by test_transforms (θ=+π/2 lands on the front edge, θ=−π/2 off-board). (2) CRITICAL arc-centroid bias ~30× too small (r_obj²/2d = 1.25 mm vs true ~36–44 mm): fixed with the mandated formula bias = r_obj·(1+cos β)/2, β = asin(r_obj/d̂), applied radially away from the lidar; Monte-Carlo-verified residual 5–14 mm. (3) MAJOR background threshold arithmetic (0.03 m claimed as 2.5σ_max but σ_max=0.02 m → 2.5σ=0.05 m; 0.03 m gave 13.4% FP/point at far corner): fixed to 2.5·σ_max — 0.10 m at the S=3.0 far corner (σ_max=0.040 m, §7); statistical test asserts <1% FP per point. (4) MAJOR min-cluster-size 2 drops far-corner single-point scans (~31% of scans): fixed by accepting 1-point clusters within the 0.5 m prediction gate; sim-verified max 1 consecutive miss at the far corner over 60 s. (5) MAJOR angle-grid/config inconsistency (2π/300 step vs 2π/299 increment vs claimed 'SDK-verified' round() formula — SDK has no such formula and its own arithmetic gives 303): fixed to N=300, θ_i = −π + i·2π/299 inclusive, angle_increment=2π/299 (SDK FOV/(count−1), CYdLidar.cpp:634-635), asserted by the size formula in test_swap. (6) MAJOR acceptance-8 'points within board bounds' contradicted by wall rays: fixed by clipping published points to the board footprint [0,S]² (wall echoes dropped from the cloud; box remains as geometry). (7) MAJOR real-swap tracker undefined (calibration was a sim-only raycast): fixed by BackgroundTable abstraction — capture-based calibration in the LidarSource ABC (sim: raycast; real: 30-scan median + interpolation to jittered angles). (8) MINOR reset path unspecified (WS thread → scan thread race): fixed by SceneModel control queue drained between doProcessSimple calls; reset applies at the next scan boundary. PLUS the design-agnostic pygame confirmed flaws that also bind this architecture: (9) MAJOR canonical option block omits LidarPropFixedResolution (real SDK then emits variable-size scans): fixed — FixedResolution=True added (verified CYdLidar.cpp:53,625-628); (10) MINOR scanFreq parity (sim pins 10.0 vs measured 4–8 Hz real): documented; tracker dt clamp [0.05,0.5] absorbs it, HUD shows reported value; (11) MAJOR shutdown race (main thread calling turnOff/disconnecting after a timed-out join): fixed — scan thread owns the source exclusively and shuts it down in its own finally; pacing sleep is stop_event.wait(); (12) MAJOR mixed-pixel pulls bias the centroid: fixed by range-consistency rejection (cluster median + 3σ) before the centroid; (13) MAJOR acceptance tolerances tighter than the noise model: exactness checks run noise-off; statistical checks use model-derived bounds; (14) MAJOR truth-marker data path: true_pose is a first-class frame field published by the scan thread (it owns the scene); (15) MINOR coordinate-sign test error (B(0.5,0.5)→θ=+π/4 vs −π/4): resolved by the corner-origin frame where atan2(x_B,y_B)=+π/4 is provably self-consistent, pinned by a round-trip test. DESIGN UPDATE (16) board size is configurable: board_size (SceneConfig.board_size, CLI --board-size), single square scalar, S ∈ [1.0, 3.0] m default 2.0, object_radius r=0.10 m (SceneConfig.object_radius — the user's pointer is ~10 cm radial); every geometry, schema, world transform, and test is parameterized by S; the 3.0 cap is the object-detection budget — the fixed 0.10 m background threshold (= 2.5·σ_r(4.24), S=3.0 worst case) must equal the 10 cm object signature, so larger panels require a larger object (r=0.17 → S=4.0). Serial-design flaws (CT byte 10× low, model-12 claim, GIL contention, aimspeed scaling, angle-correction residual, torn pose race) do not apply — the pty approach is rejected. DESIGN CHANGE (17) game decoupled from the web: the game was originally specced as a second web page (/game) on the FastAPI server; it is now a standalone desktop app (game/, pygame window, own process) sharing only the web-free core (core/: lidar + tracker); the web server is a testing-only tool for the pre-radar phase and contains no game code; the game requires no web server. The /game WS channel and game.html/game.js were removed from the design.

## 16. Rejected approaches

PYGAME (7.70): The leanest build — one process, pygame-ce + numpy + no server/WS/browser — and its engine package mirrors the SWIG surface via a Protocol with a clean sim/render split, but the manual 3D projection caps visual quality (viz 6.0 vs webgl 9.0: no lighting, no shaders, hand-rolled depth/transparency and text HUD), ties the demo to the workstation display with no remote/browser path, and reintroduces the Wayland/X11 GL friction the context explicitly said the browser avoids; the hand-maintained projection + CW/left-handed coordinate math is its own highest-risk area (multiple confirmed sign/consistency flaws), and its Kalman tracker adds tuning surface beyond the alpha-beta used elsewhere. It wins deps_weight and dev_effort but trades away exactly the polish and portability that make the demo compelling, so on the weighted total it loses. NOTE: this rejection governs ONLY the 3D visualizer; the game UI is a web-free 2D pygame window (§10), where pygame is the right tool — the two verdicts are unrelated.

SERIAL (6.80): The highest behavioral fidelity — the real SWIG driver runs against a pty streaming authentic X3 protocol bytes (115200 8N1 pacing, checksums, 1/64° angles, LSN≤40, A5 command state machine), exercising the SDK's decode path exactly as hardware would — but that fidelity is bought at the highest cost and risk: 4 threads, a protocol codec, byte-level pacing, and a stack of admitted hacks (the driver CERTAINLY reports model 12 (S2) not 6 — and even that is unobservable through the public SWIG API; the ~6° angle-correction must be pre-subtracted with a residual that is not exact for intermediate samples; the sim path's single point of failure is the real C++ serial layer accepting the emulated packets). Its own confirmed flaws include a 10× CT-byte frequency error, GIL contention during the blocking grabScanData, and a torn-pose race; it is also the slowest path (6 Hz, 500 points) with the heaviest runtime (ydlidar required even for sim). The fidelity advantage does not pay off in the weighted total (6.80 vs 7.99), so it is rejected despite the best drop-in story.

## 17. Acceptance criteria

Corrected for the fixed math (Monte-Carlo-verified with the full noise model + tracker): (1) python -m web.run --lidar sim serves the page; browser shows the box, board, lidar marker at world (−S/2,−S/2) (board front-right corner), live cyan cloud, red track marker, HUD readout at ~10 Hz; no console errors. (2) Noise-off raycast exactness vs analytic ground truth: |err| < 1e−9 m (walls, board edges, object occlusion, blind spot). (3) TRACKING ACCURACY (realistic): over a 60 s scripted path within the board the path scales with S (worst case S=3.0: object 0.45–2.55 m from the lidar, including the far corner): median |tracked − true_pose| ≤ 2.5 cm and p95 ≤ 5 cm (sim-verified: median ≈ 11 mm on a moving path, ≈ 21 mm static at the far corner; p95 ≈ 19 mm / 35 mm) — the old 1.5 cm median / 3 cm p95 numbers were impossible given the arc-centroid residual and are replaced by ~3 cm realistic accuracy. (4) Track continuity: at dropout 2% / ghost 0.1% / mixed pixels, the track is never lost for > 3 consecutive scans over 60 s anywhere on the board (sim-verified: max 1 consecutive miss at the far corner, 0 on the moving path). (5) Latest-wins: after a 5 s backgrounded tab, the first shown frame seq equals the server's current seq. (6) Swap: test_swap.py asserts the ABC surface parity with the installed ydlidar module and config consistency; --lidar real runs the identical code path with captured-background calibration (hardware swap = CLI flag, zero consumer changes). (7) Reset: client reset re-seeds the sim and re-calibrates the background at the next scan boundary without a client restart. (8) Wire: every frame parses per the schema, points are within the board footprint [0,S]², seq is monotonic, hello/scene precede frames, and the browser performs no trigonometry. (9) Background false-positive rate < 1% per point across the board with the 0.10 m threshold (statistical test). (10) Board-size configuration: config.board_size / --board-size accepts S ∈ [1.0, 3.0] m (square by construction), rejects out-of-range with a clear error; hello/scene/frames/browser stay consistent with S (verified at S=1.0 and S=3.0). (11) GAME (desktop, web-free): python -m game.run --lidar sim --image-x x.png --image-o o.png opens a pygame window showing the 3×3 grid; taps map to cells per the rounding rule (cell center → that cell; near an edge → the containing cell); overwriting the opponent's cell works; win detected per tap; New Game resets; the resolution control changes the rendered size; the hover cell tracks the pointer; X/O glyphs come from the image files (vector fallback when missing); the game runs with NO web server started. (12) TAP DETECTION: no tap outside the board, no re-fire before release, dwell ≈ 0.3 s, taps ignored while the game is inactive.
