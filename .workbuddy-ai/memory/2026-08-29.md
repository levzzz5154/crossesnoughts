## Code review of the repo (from HANDOFF.md + source audit)

Reviewed the handoff doc and read core/tracking.py, core/config.py, core/noise.py,
core/game.py, web/main.py, game/run.py, game/render.py. Findings (unfixed, report only):

1. **The game does not play from the lidar.** `game/run.py:72-79` computes
   `res = tracker.process(scan)` then only tests `res is not None`; the tap
   position `px,py` comes from `pointer{}`, which is written solely by
   MOUSEMOTION. `game/render.py` draws no tracked marker. So in `--lidar real`
   a real finger/pointer still does nothing — the lidar is just a 10 Hz gate.
   HANDOFF §6 understates this ("interactive play requires --lidar real").
2. **Dwell timer bug.** `TapDetector.update` compares against the pointer sample
   timestamp `pointer["t"]`, which only advances on MOUSEMOTION. Holding the
   pointer perfectly still → `t - entered` stays 0 → the tap never fires. The
   e2e test masked it by using continuous ~0.3 m/s motion (HANDOFF §7.5).
   Fix: pass `time.monotonic()` at scan time, not the sample timestamp.
3. **`TrackResult.conf` is computed and serialized but never consumed** by
   web/main.js or game/render.py — only asserted in test_wire.py. A track
   coasted through 10 misses renders identically to a live one.
4. **Acquisition vs tracking disagree on cluster selection.** `_acquire` takes
   the LARGEST cluster with no width/size sanity check; `_process` prefers the
   NEAREST gate-passing cluster. Extract shared `_centroid(ca,cr)`, and add a
   subtended-width check: a real finger subtends ~2*asin(0.05/d) rad (~2.9 deg
   at 2 m); grazing-angle board/wall false positives subtend far more.
5. **Noise model has no incidence-angle term.** sigma = a + b*d^2 is radial only.
   At S=2.0 much of the board is seen at >70 deg incidence, where real spread
   exceeds the model. Expect real BG false-positive rate >> the 1% measured in
   sim. Suggested mitigation: sigma_eff = sigma(r)/cos(phi), clipped.
6. Real-lidar path is entirely untested. Recommend a record/replay harness:
   dump raw scans to npz, replay through Tracker offline as a pytest.
7. UX: overwrite-any-cell + 0.3 s dwell means a lingering hover silently steals
   a cell and can win the game. Want a dwell progress ring + longer dwell
   (~0.8 s) to overwrite.

Opinion: architecture is good (single-writer scan thread, SWIG duck-typing for
the sim, latest-wins boundary, arc-centroid bias correction). Disagree with
HANDOFF §10 priority: shared web/game state should be LAST, not first — coupling
two processes means a tracker bug takes down both during bring-up.

## Built: record/replay (core/recording.py)

User asked "can we record real lidar data and play it back in the web viz". Yes —
implemented and verified end to end.

- `RecordingLidarSource` wraps ANY source via `__getattr__` delegation (so sim
  extras keep working), captures every scan `doProcessSimple` returns, flushes
  to compressed .npz every 60 scans + on `close()` + via `atexit`.
- `ReplayLidarSource` subclasses LidarSource, paces by recorded stamps, supports
  loop / speed (0 = free-run) / seek. `reset` control rewinds to scan 0.
- Non-looping playback exposes `exhausted`; ScanLoop breaks instead of spinning.
- Format: ranges (T,N) f32, angles (T,N) f32 (collapsed to (N,) when uniform),
  stamps (T,) i64 ns, optional bg_angles/bg_ranges f64, meta JSON string.
- `make_lidar_source` gained `replay` kind + `replay_path/loop/speed` and
  `record_path/record_note`. Both CLIs and `python -m core.recording` wired.
- web/main.py: replaced `getattr(source,'reset')` sim detection with capability
  checks (object_pose => sim, seek => replay); finally now calls turnOff,
  disconnecting, close.
- Removed a dead duplicate block in core/sim.py (set_object_pose/object_pose/
  scan_freq/reset were each defined twice).

**Trap found by tests:** `record()` initially skipped `calibrate_background()`,
so the file had no bg and replay fell back to a median computed from scans that
already contained the object. Median tracking error 0.53 m. Fixed by capturing
the background before the first recorded scan (mirrors what ScanLoop does);
error then <0.05 m. Always capture bg before recording.

**Trap 2:** `--replay-speed 0` finishes a 31-scan recording in ~30 ms, so the
latest-wins SceneModel only lets the WS client sample ~3 frames. Free-run is
for headless analysis; use a paced speed to watch. web/run.py now warns.

Tests: tests/test_recording.py, 18 cases. Full suite 88 passed (was 70).
Live smoke verified: CLI record, server --record, paced replay monotonic with
tracker held 22/22, free-run emitted exactly 31 frames then stopped, looping
wrapped twice in 8 s, reset rewound scan 8 -> 0.

HANDOFF.md updated: §2 flags, §4 module map, §6 bug notes, §8 evidence,
§9 gotchas, new §11 record/replay, next steps renumbered/re-ranked.

## Bug found + fixed: _acquire picked the largest cluster

Bigger than bugs 1-2. With a STATIC object at (1.0, 1.0), seed 5, BG subtraction
yields two clusters of EQUAL size: n=3 r=2.05 m at (1.42,1.47) = the object's own
mixed-pixel points pulled halfway to the board behind, and n=3 r=1.34 m at
(0.99,0.90) = the clean object. `_acquire` took the largest, ties broken by angle
order → locked onto the fragment 0.70 m behind the object, then held it forever
with missed=0 / conf=1.0 because the real object is outside the 0.5 m gate.
Position+seed dependent: failed at seed 5 only, seeds 11/23 fine — that is why it
survived all testing.

Fix: `_acquire` now takes the NEAREST cluster (matching `_process`), plus extracted
a shared `_centroid(ca, cr)` helper so the two paths cannot drift, and dropped the
dead `or best is None` in `_process` (best_r starts at inf).
Evidence: 8 positions x 3 seeds — 3 broken cases fixed, none made worse; worst-case
static error 70.4 cm -> 1.9 cm. New guards in tests/test_tracking.py; verified they
are not vacuous (3/12 acquisition + 2/2 convergence cases fail under the old rule).

**Debug trap:** do NOT investigate the tracker with `SimLidarSource._scan_freq`
raised (e.g. 500) to skip wall-clock time. `Tracker._dt` clamps to [0.05, 0.5] s,
so dt=0.05 vs 2 ms elapsed = 25x velocity exaggeration, and it manufactures a
"phantom latch" that does NOT reproduce at the real 10 Hz (where missed climbs,
the track drops after 10 misses and re-acquires correctly). Fine for recording
fixtures; not for tracker dynamics.

Suite: 96 passed (was 88 -> 92 -> 96).

## Fixed: game plays from the lidar + dwell clock (bugs 1 & 2)

game/run.py rewritten:
- New `--pointer {lidar,mouse}`, default `lidar`. lidar mode commits moves from
  the tracked position. In SIM mode the mouse acts as the hand (calls
  set_object_pose), so the whole raycast->noise->tracking pipeline is exercised;
  with real hardware or replay the mouse is ignored entirely.
- Dwell clock = `time.monotonic()` per scan, not the pointer sample timestamp.
- `res is None` or hand off board -> `tap.release()` (finger lifted).
- `res.missed > 0` -> release too: a coasting track is a prediction, and a jump
  would otherwise put a phantom dwell on the OLD cell.
- Hover + a new amber pointer ring in game/render.py follow the tracker and fade
  with `conf` (first consumer of conf).
- `MOUSE_JUMP_RESET = 0.5` m: mouse moves the object further than that in one
  scan -> `tracker.reset()` so it re-acquires (mirrors web click-drag).

**Bug in my own first attempt:** gating taps on "mouse on board" would have
blocked ALL taps in `--lidar real`, where the mouse never moves. Guard is now
`mouse_drives_hand` (mouse mode, or lidar+sim); in real/replay mode
"hand on board" simply means "a track exists".

## Confirmed tracker bug (still open, now fully characterised)

Single-point clusters are accepted as measurements. Measured with the object at
(0.333,0.333) and the track at (1.0,1.0): scan holds an 11-point and a 6-point
cluster (the real object, r~0.38 m) plus three SINGLE-point mixed-pixel outliers
at r=1.41-1.56 m. Object is 1.03 m from the track -> rejected by the 0.5 m gate;
the single outlier at (1.13,1.08) is 0.15 m away -> accepted. Tracker then
follows the phantom with missed=0 and conf=1.0 and never self-corrects.
`core/tracking.py:105-107` explicitly allows 1-point clusters inside the gate.
=> Any jump beyond the gate needs Tracker.reset() (game + web do this); real
hardware has no reset to call, so the acceptance rule must be fixed.
core/tracking.py constants are acceptance-coupled — needs user sign-off.

Verification: 92 tests pass. Real app driven in-process (SDL dummy) with ONE
mouse move then 3 s held still commits exactly one move in both modes; lidar
mode lands 0.54 cm off the raw mouse point (proving it went through tracking),
mouse mode lands exactly on it. Before: lidar committed 2 phantom moves at the
old position, mouse committed none.
