## YDLidar X3 hardware verified live

Probed the X3 the user plugged in. Confirmed working end to end.

- Device: `/dev/ttyUSB0`, Silicon Labs CP2102 USB-UART bridge (`10c4:ea60`),
  stable symlink `/dev/serial/by-id/usb-Silicon_Labs_CP2102_USB_to_UART_Bridge_Controller_0001-if00-port0`.
- Permissions fine: `root:uucp 660` and `levzzz` is in the `uucp` group.
- **Baud is 115200** (not the SDK default 230400). Derived by decoding the raw
  triangle-protocol stream; cross-checked against `YDLidar-SDK/python/examples/tri_test.py`.
- It auto-streams on power-up — no SCAN command needed to see data.

Measured (4 s capture, raw parse, zero dropped packets):

| metric | value |
|---|---|
| checksum pass rate | 100% |
| rotation | 12.10 Hz (82.6 ms/rev) |
| points / revolution | 331 (~1.09 deg/point) |
| ranging rate | ~4.0 kHz |
| angular span / rev | 360.3 deg |

Independently confirmed with the real SWIG SDK (`YDLidar-SDK/build/python`):
`initialize()` at 115200 succeeded, health "good", 37 scans / 3.06 s = 12.1 Hz,
330-331 pts/scan, "Sample Rate: 4.52K". Raw and SDK numbers agree.

Protocol constants used (from SDK source, for future decoding):
angle = `(raw >> 1) / 64.0` deg (CYdLidar.cpp:659); range = `raw / 4000.0` m
(CYdLidar.cpp:685); checksum = XOR of the four header u16s then every node u16
(YDlidarDriver.cpp:1472).

## Two blockers found in real mode

1. **System `python3` (3.14) segfaults on `ydlidar.CYdLidar()`.**
   `_ydlidar.so` links `libpython3.12.so.1.0` from miniconda3. Running it under
   3.14 is an ABI mismatch -> SIGSEGV (rc 139). Must use
   `/home/levzzz/miniconda3/bin/python` (3.12.11), which has numpy, fastapi,
   uvicorn, pygame, pytest and serial all present.
   Also needs `PYTHONPATH=<repo>/YDLidar-SDK/build/python`.

2. **`core/real.py` never applies the canonical option block.** Its docstring
   claims it mirrors `tri_test.cpp`, but no code in core/, game/ or web/ ever
   calls `setlidaropt` for the real source. `RealLidarSource.__init__` only
   stores the port. So `initialize()` runs on SDK defaults, and
   `LidarPropSerialBaudrate` defaults to **230400** -> fails against this
   115200 device. Needs the tri_test option block (at minimum baud + port +
   TYPE_TRIANGLE + YDLIDAR_TYPE_SERIAL).

## Real-vs-sim constant mismatch

`core/scan.py` hardcodes values that do not match the hardware:

| constant | in code | measured |
|---|---|---|
| SCAN_POINT_COUNT | 300 | 331 |
| SCAN_FREQ | 10.0 Hz | 12.1 Hz |
| SCAN_SAMPLE_RATE | 3.0 kHz | ~4.0 kHz |

Also `scan.moduleNum` came back 0 from the SDK, not `MODULE_NUM_X3` (=6);
`core/real.py:doProcessSimple` overwrites it manually.

## Documented software survey (read-only, no execution)

Catalogued what the bundled YDLidar-SDK **1.2.20** docs describe for the X3.

- `doc/Dataset.md` X3/X3 Pro row: model 6, **115200**, SampleRate 3K,
  range 0.10-8.0 m, scan frequency **4-8 Hz (PWM)**, SingleChannel **true**,
  4.8-5.2 V. Baud and single-channel match what we measured; the documented
  4-8 Hz and 3K disagree with the measured 12.1 Hz and ~4.0 kHz.
- Docs say explicitly: run `tri_test` for triangle units.
- Only X3-correct samples: `examples/tri_test.cpp`, `tri_restart.cpp`,
  `tri_and_gs_test.cpp`, and `python/examples/tri_test.py` (115200,
  TYPE_TRIANGLE, YDLIDAR_TYPE_SERIAL, SampleRate 3, SingleChannel True).
- The two official matplotlib viewers (`plot_ydlidar_test.py` 230400/SR 9,
  `plot_tof_test.py` 512000/TYPE_TOF) are **wrong for the X3 as shipped** —
  which is why `tools/lidar_view.py` is worth keeping.
- Everything else in `examples/` (tof, gs, tea, tia, scl, sdm, tmini, et) and
  `python/examples/` targets other models/bauds.
- Language bindings: C++, C (`lidar_c_api_test.c`), Python (SWIG, `pip install .`),
  C# (SWIG, needs `cmake -DBUILD_CSHARP=ON`, not built here). Other languages
  "through swig" per Software_FAQs. Ubuntu + Windows only, officially.
- **No ROS/ROS2 driver anywhere in the tree** — only doc comments in
  `core/common/ydlidar_def.h` / `ydlidar_datatype.h` mention
  `sensor_msgs::LaserScan`. YDLIDAR ships ROS drivers in separate repos.
- External, referenced but not bundled: `github.com/YDLIDAR/ydlidar_tutorials`
  (c_/cpp_/python_tutorials + CommunicationProtocol),
  `github.com/YDLIDAR/DemoProject/YDLidar-SDK-Source-Demo`, upstream wiki.
- `doc/howto/how_to_create_a_udev_rules.md` documents making a stable
  `/dev/ydlidar` symlink — nicer than `/dev/ttyUSB0` if the port ever moves.
- Broken doc links in this checkout: `doc/quickstart/README.md` points at four
  `ydlidar_sdk_1_0_0_*.md` files that are not present.

   TYPE_TRIANGLE, YDLIDAR_TYPE_SERIAL, SampleRate 3, SingleChannel True,
   FixedResolution True) before `initialize()`. Previously used SDK defaults
   (baud 230400) and failed against the 115200 device.
2. `core/game.py` — own-cell tap is now a no-op (no move, no turn flip).
   Overwriting opponent's cell still allowed + flips turn.
3. Pipeline scan-then-move ordering bug: after a pointer jump + tracker reset,
   the scan was captured *before* the sim object moved, so the tracker
   re-acquired at the old position. Fixed: move the sim object first, then
   capture the scan.
4. Slider `fmt` attr: was called as `self.fmt.format(self.value)` but `fmt`
   is a function, not a format string. Fixed to `self.fmt(self.value)`.

## Post-build fixes (same day)

Four issues the user spotted:

1. **Min board size too big** — was 1.0 m, lowered `BOARD_SIZE_MIN` to 0.1 m
   in `core/config.py`. Slider range in settings screen updated to match.
2. **Yaw slider doesn't update in real-time** — Slider class only fired
   `on_release` on `MOUSEBUTTONUP`. Added `on_change` callback that fires
   during `MOUSEMOTION` drag; yaw now rotates the radar overlay live as you
   drag. Board size also gets live updates, but the sim source rebuild is
   deferred to release (via `set_board(rebuild=False)` during drag,
   `rebuild=True` on release) to avoid flicker.
3. **Keyboard input for slider values** — clicking a slider focuses it;
   typing digits builds a number (with decimal point support), Enter applies
   it, Escape cancels. Arrow keys nudge by one step. Enter no longer starts
   the game while a slider is focused.
4. **Tracking shouldn't go past the board** — the pipeline now clamps the
   tracked x/y to `[0, board_size]` before publishing, so the pointer ring,
   cell highlight, and tap can never land outside the board even when the
   tracker coasts on a prediction or mixed-pixel pull overshoots.

Tests: 118 passed (updated `test_config_validation` and
`test_values_normalized` for the new BOARD_SIZE_MIN). Headless smoke test
passes.
